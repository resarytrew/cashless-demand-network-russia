## Точная цель алгоритма

Алгоритм сравнивает наблюдаемые связи внутри групп с ожидаемыми связями узлов такой же общей силы. Для всей расширенной сети:

```text
Qγ = (1 / 2m) Σu,v [Wuv − γ su sv / (2m)] · 1(cu = cv)
su = Σv Wuv
m = (1/2) Σu,v Wuv
```

W — взвешенная матрица связей, s — сила узла, m — суммарный вес неориентированных рёбер. Сила включает межмесячные связи. Ожидаемая связанность рассчитывается по всей сети, а не отдельно по слоям. Это ordinary weighted modularity на expanded supra-graph, не классическая multislice modularity. Такая формулировка важна для понимания временного сглаживания и разрешения групп.

Оптимизируемое Q при γ=0,5 нельзя смешивать с отчётной conventional MQ при γ=1. [Исходная спецификация](TEMPORAL_MODEL_SPECIFICATION.md) сохранена без редактирования. Номера сообществ произвольны; A–G относятся к основным базовым профилям, а не ко всем сообществам во всех постановках.

## Сохранение участников и точность границы

Для базовой группы R и группы назначения S с наибольшим пересечением:

```text
retention = |R ∩ S| / |R|
destination precision = |R ∩ S| / |S|
destination Jaccard = |R ∩ S| / |R ∪ S|
```

При равном пересечении выбирается наименьший номер группы назначения. Несколько базовых групп могут иметь одну группу назначения. Числа нельзя читать как взаимозаменяемые оценки «качества». Для муниципалитета отдельно учитывается совместное попадание с его базовыми соседями по группе и характеристики его группы назначения; определения и агрегация сохранены в коде и первичных таблицах.

## Как собирается карта устойчивости

Частота совместного попадания пары не зависит от номера сообщества. Для семейства f с n_f запусками и пары i,j:

```text
C_f(i,j) = (1/n_f) Σr 1(c_i,r = c_j,r)
C(i,j) = 0.25 × Σf C_f(i,j)
a(i,g) = среднее C(i,j) по j из базового g, исключая j=i
p(i,g) = a(i,g) / Σh a(i,h)
margin(i) = p(i,первый) − p(i,второй)
entropy(i) = −Σg p(i,g) ln p(i,g) / ln(7)
```

Четыре семейства: perturbation (50), alpha (2), gamma (3), algorithm (1). Равные веса не позволяют 50 perturbation-запускам автоматически подавить одно алгоритмическое сравнение. `p` здесь — нормированная доля близости, не статистическая вероятность. Большая entropy означает распределённую близость, малый margin — слабое преимущество ведущего профиля. При нулевой суммарной близости класс unresolved, entropy не определена. Равенства долей разрешаются стабильным порядком профилей.

Категория устойчивости определяется отдельно по perturbation-диагностике, не просто максимальной долей близости:

| Категория | Правило |
|---|---|
| stable_core | peer ≥0,85; precision ≥0,75; Jaccard ≥0,65 одновременно |
| expansive_core | peer ≥0,85, но precision <0,75 или Jaccard <0,65 |
| transition | peer <0,75 и Jaccard <0,50 |
| unresolved | остальные случаи; также технический micro-профиль |

`peer` — агрегированное совместное попадание с участниками исходного профиля. Expansive core сохраняет окружение, но не достаточно определённую границу. Основной текст не приравнивает его к ядру с точной границей.

При исключении одного семейства сравниваются новые ведущие классы и близости. Для чувствительности к опорным участникам используется верхняя четверть по близости к собственному профилю, минимум два участника. Направление D/G требует согласия минимум трёх семейств. Эти операции не являются внешней валидацией. [Настройки](../configs/stability_atlas_v2_2_1.yaml) · [Определения](../src/sbernet/robustness/soft_consensus.py) · [Чувствительность](../src/sbernet/robustness/soft_consensus_v2_2.py).

## Внешние проверки: что именно означает p

Порядок Алтая задан как G=1/F=2/D=3; положительный ρ означает более высокую зарплату в направлении D. Спирмен использует двусторонний приближённый p с сохранением повторяющихся рангов. При n=6 это не точный перестановочный тест.

Якутская регрессия: `ln(salary_2024) ~ const + ln(investment_per_capita_2024) + ln(population_2024) + urban_share_2024`, ковариация HC3, нормальное приближение, `use_t=False`.

Алтайская регрессия: `ln(salary_2024) ~ const + profile_rank + ln(population_2024) + urban_share_2024`, обычная ковариация, t-распределение, `use_t=True`, две остаточные степени свободы. Её p=0,088869 не является поправкой на множественные сравнения к p=0,008050 Спирмена. Такой поправки в сохранённых расчётах нет.

Хабаровск: двусторонний Mann–Whitney, `method=auto`, continuity correction включена; Cliff's delta ориентирована A минус G. Чукотские медианы не имеют p-value. Все выводы поисковые. Временная связь зарплат за два года не подменяет устойчивость сетевого разбиения.

## Проверка вычислений и границы общего manifest

Инструкции установки зависимостей сохранены в [описании воспроизведения](ROUND17_REPRODUCTION.md). После установки, из корня репозитория в PowerShell:

```powershell
$env:PYTHONPATH = 'src;.;scripts'
$env:PYTHONUTF8 = '1'
python -m pytest -q
python scripts/run_round17_external_validation.py
```

Первая команда запускает полный набор тестов; вторая проверяет уже завершённый внешний пакет без перезаписи. Для нового внешнего воспроизведения нужен отдельный пустой каталог. Первичные внешние документы при этом не восстанавливаются: входом служит нормализованная таблица.

Общий `scripts/verify_current_artifacts.py` проверяет не только результаты, но и хеш README на момент вычислительного релиза `3c988699118f7718e1ea1bfeed8c111d157e8de9`. Поэтому новая публичная редакция README закономерно не совпадает с историческим хешем. Это нельзя скрывать изменением старого manifest или считать изменением научных результатов. Прежний README побайтово сохранён как [PUBLICATION_BASELINE_README.md](PUBLICATION_BASELINE_README.md); исходные manifests и verifier не редактировались.

Для независимой проверки целого исторического вычислительного состояния можно создать отдельный checkout:

```powershell
git worktree add --detach ../sber-computation-check 3c988699118f7718e1ea1bfeed8c111d157e8de9
Push-Location ../sber-computation-check
$env:PYTHONPATH = 'src;.;scripts'
$env:PYTHONUTF8 = '1'
python scripts/verify_current_artifacts.py
Pop-Location
```

Эта проверка относится к указанной ревизии. Равенство её кода, конфигураций и результатов текущей версии проверяется **отдельно**, а не выводится из успешного старого checkout:

```powershell
git diff --exit-code 3c988699118f7718e1ea1bfeed8c111d157e8de9 -- src scripts configs data outputs reference tests pyproject.toml
```

Отсутствие изменений в перечисленных путях связывает историческую проверку с текущими вычислительными файлами. Неотслеживаемые файлы требуют отдельного просмотра `git status --short`. Этот публичный релиз не содержит новых данных или вычислительного кода.

С разрешения пользователя отдельно адаптирован только workflow CI. Он запускает тесты на текущем checkout, затем экспортирует **текущий коммит** во временную папку. Только README и сам workflow заменяются там прежними байтами из `PUBLICATION_BASELINE_README.md` и `PUBLICATION_BASELINE_VERIFY.yml`, после проверки их SHA256 по неизменённому manifest. Все вычислительные файлы, результаты и manifests берутся из текущего коммита и проходят прежний verifier без исключений. Основное рабочее дерево не меняется. Это явное отделение редакции и CI от научной целостности, не проверка одних старых результатов вместо текущих.
